## ApiLens v0.11.1 — YAML 요청을 받지 않습니다 · 빌드 도구 정비 | The server no longer accepts YAML · build tooling refresh

**collector(server) jar 만 바꾸면 되는 정비 릴리스입니다. agent 코드는 바뀌지 않아 다시 배포하지 않아도 됩니다** —
0.11.0 agent 를 그대로 쓰면 됩니다. 서버가 **YAML 로 요청을 받지도, YAML 로 답하지도 않게** 바뀌었습니다. YAML 본문은
`415`, 응답을 YAML 로만 받겠다는 요청은 `406` 을 받습니다(오류로 끝나는 일부 요청은 `500` — 아래 참고). API 문서의
YAML 판(`/v3/api-docs.yaml`)은 그대로 열립니다.
agent 와 화면은 JSON 만 쓰므로 영향이 없고, **YAML 로 직접 보내던 스크립트 · 도구만** JSON 으로 바꾸면 됩니다.
그 밖에 빌드 도구(Gradle 9.9.1)와 화면 빌드 Node 판(24)을 올리고, 서버 컴파일 경고를 정리하고, 자동 시험을 보강했습니다.

**DB 스키마는 바뀌지 않습니다** — 마이그레이션이 없어, 되돌리려면 이전 jar 로 바꾸기만 하면 됩니다. 백업을 복원할
필요가 없습니다. 화면 왼쪽 위 버전 라벨은 **`v0.11` 그대로**입니다 — 판은 `/v3/api-docs` 의 `info.version`(`0.11.1`)으로
확인하세요.

**A maintenance release — replace only the collector (server) jar. The agent code is unchanged, so you can keep using
the 0.11.0 agent.** The server **no longer reads or writes YAML**: a YAML request body now gets `415`, and a request that
accepts only YAML gets `406` (`500` for some requests that end in an error — see below). The YAML form of the API
document (`/v3/api-docs.yaml`) stays available. The agent and the web UI only use JSON and are not affected; only scripts
or tools that sent YAML directly need to switch to JSON. The build tooling moves to Gradle 9.9.1, the web UI is built
with Node 24, server compiler warnings are cleaned up and the automated tests are extended. **No database migration** —
rolling back is just swapping the jar. The version label in the top-left corner **stays `v0.11`**; check `info.version`
(`0.11.1`) in `/v3/api-docs`.

---

### YAML 요청에 대한 응답이 바뀝니다 | Breaking change: YAML requests

- **YAML 본문(`Content-Type: application/yaml`)을 보내면 `415` 를 받습니다.**
  - 수집 입구 `POST /v1/spans` 는 전에는 YAML 본문을 `202` 로 받았습니다. `POST /v1/setup/complete` 는 `200` 으로
    받았습니다. 요청 본문을 받는 다른 API 도 같습니다.
  - 거절된 본문은 저장되지 않습니다.
- **응답을 YAML 로만 받겠다고 한 요청(`Accept: application/yaml` 하나)은 오류 없이 처리되면 `406` 을 받습니다.**
  전에는 `200` 과 YAML 응답이었습니다(예: `GET /v1/services`). YAML 과 JSON 을 함께 적은 요청은 JSON 으로 답합니다.
  - 오류로 끝나는 요청 가운데 일부(없는 trace 조회 · 잘못된 span id 를 담은 수집 요청 등)는 YAML 로만 받겠다고 하면
    `500` 을 받고, 수집기 로그에 `ERROR` 와 스택이 남습니다(0.11.0 은 이 두 요청에 `404` · `400` 으로 답했습니다).
    `application/xml` 처럼 서버가 내지 않는 다른 형식만 받겠다고 한 요청과 같은 동작입니다.
- **API 문서의 YAML 판 `/v3/api-docs.yaml` 은 그대로 `200` 입니다.** `/v3/api-docs`(JSON) · `/swagger-ui` 도 그대로입니다.
- **누가 영향을 받나** — YAML 로 직접 요청을 보내거나 YAML 응답을 받던 스크립트 · 도구뿐입니다. agent 는 JSON 만
  보내고, 화면도 JSON 만 씁니다.
- **왜 바꿨나** — 0.10.0 에서 JSON 본문의 숫자 칸 `null` 과 올바른 JSON 뒤에 더 붙은 글자를 `400` 으로 거절하게
  바꿀 때, YAML 본문은 그 변경 밖이라 같은 경우를 `202` 로 받았습니다(숫자 칸 `null` 은 0 으로 저장). 이번에 그 YAML
  입구를 닫아, 인증 없이 열린 수집 입구가 받는 본문 형식이 JSON 하나가 됐습니다.

### 바뀐 것 | Changed

- **빌드 도구** — Gradle wrapper 8.14.6 → 9.9.1 · agent jar 를 묶는 shadow 플러그인 8.3.5 → 8.3.11.
  - agent jar 안의 클래스와 파일은 0.11.0 과 같습니다. 다른 것은 버전 표시 두 곳(`agent-version.properties` ·
    manifest 의 `Implementation-Version`)뿐입니다.
  - 직접 빌드할 때는 wrapper 가 Gradle 9.9.1 을 받아 씁니다. JDK 는 21 그대로입니다.
- **화면 빌드 Node 24** — CI 와 릴리스 빌드가 화면을 Node 24 로 짓습니다. 직접 빌드할 때 지원하는 Node 판은
  24 이상입니다.
- **컴파일 경고 정리** — 서버 소스의 컴파일 경고를 0 으로 맞췄습니다. 동작은 바뀌지 않습니다.
- **자동 시험 보강** — 토큰 없이 두 번 인코딩한 `..` 경로로 보호된 조회를 읽을 수 없는지, Spring Boot 지원 기간
  경고가 끝 날짜 앞 · 당일 · 뒤에 맞는 줄을 내는지, 밤 정리의 빈 공간 회수가 실패했을 때와 WAL 체크포인트가 막혔을
  때의 로그 줄, 밤 정리와 데이터 받기가 겹칠 때 받은 데이터를 잃지 않는지를 시험이 지킵니다. 이 시험들로 바뀐 제품
  동작은 없습니다.
- 문서: 보안 공지 대조표(`docs/security.md`)에 표마다 「확인 시각」 칸을 더했습니다. 공지 내용과 판정은 그대로입니다.
  README 「현재 한계」에서 YAML 본문 줄을 뺐습니다.
- **버전 0.11.0 → 0.11.1** (collector jar · agent jar).

### 이렇게 보여도 정상 | Looks odd, but expected

- **서비스 목록의 agent 버전이 `0.11.0` 으로 보입니다.** agent 를 다시 배포하지 않았다는 뜻이고 정상입니다.
- **화면 왼쪽 위 라벨이 `v0.11` 그대로입니다.** 라벨은 앞 두 자리만 표시합니다. 판은 `/v3/api-docs` 의
  `info.version` 이 정확합니다.
- **YAML 요청을 `415` · `406` 으로 거절할 때마다 수집기 로그에 `WARN` 한 줄이 남습니다** — `415` 는
  `HttpMediaTypeNotSupportedException`, `406` 은 `HttpMediaTypeNotAcceptableException` 을 적은 줄입니다. 요청 하나에
  한 줄이고, 수집기는 그대로 동작합니다. 위에 적은 오류 요청의 `500` 은 `WARN` 대신 `ERROR` 와 스택을 남기고,
  수집기는 역시 그대로 동작합니다.
- **jar 안 파일 날짜가 모두 1980-02-01 로 보이고, agent jar 파일은 약 120 KB 커집니다.** 빌드 도구가 jar 를 묶는
  방식이 바뀐 결과입니다. agent jar 안의 클래스는 그대로입니다.

### 업그레이드 | Upgrade

1. **YAML 로 요청을 보내던 스크립트 · 도구가 있으면 JSON 으로 바꿉니다.** agent 와 화면만 쓰는 설치는 할 일이 없습니다.
2. **수집기를 정상 종료합니다.**
3. **collector jar 를 `apilens-server-0.11.1.jar` 로 바꾸고 다시 띄웁니다.** 이 버전은 **DB 스키마를 바꾸지 않습니다**.
   백업은 평소 습관대로 떠 두면 좋지만, 이번 버전을 올리기 위해 반드시 필요한 단계는 아닙니다.
   API 키를 켜 둔 수집기는 다시 띄울 때도 같은 키를 전과 같은 방법(`APILENS_AUTH_API_KEY` 또는
   `-Dapilens.auth.api-key`)으로 넘기세요 — 넘기지 않으면 인증이 꺼진 채 뜹니다. 기동 로그에 `API key not configured`
   경고가 있으면 키가 빠진 것입니다.
4. **agent 는 그대로 둡니다** — 0.11.0 agent 를 그대로 쓰면 되고, 대상 앱을 재시작할 필요도 없습니다. 서비스 목록의
   agent 버전 라벨을 `0.11.1` 로 맞추고 싶을 때만, collector 가 떠 있는 것을 확인한 뒤 새 agent jar 로 바꾸고 대상
   앱을 재시작하세요.
5. **열려 있던 브라우저 탭은 새로고침하세요.**
6. **새 설정 항목이 없습니다** — 설정 파일이나 JVM 옵션을 손댈 필요가 없습니다.

- **되돌릴 때**: **collector jar 만 0.11.0 으로 바꾸면 됩니다.** 스키마와 저장 형태가 그대로라 백업을 복원할 필요가
  없습니다. agent 를 0.11.1 로 바꿨다면 그대로 두어도 됩니다 — agent 코드가 같습니다.
- **API 모양** — JSON 요청 · 응답의 경로와 필드 이름 · 타입은 그대로입니다. 달라진 것은 YAML 요청에 대한 응답
  (`415` · `406`, 오류로 끝나는 일부 요청의 `500`)입니다.

> **Collector-only maintenance release — keep the 0.11.0 agent, no database migration.** Breaking change for YAML
> clients: a request body sent as `Content-Type: application/yaml` now gets `415` (before: `POST /v1/spans` answered
> `202` and `POST /v1/setup/complete` answered `200`; every other API that takes a request body behaves the same), and a
> request whose `Accept` lists only `application/yaml` now gets `406` when it is handled without an error (before: `200`
> with a YAML body, e.g. `GET /v1/services`); a request that accepts both YAML and JSON is answered in JSON. Rejected
> bodies are not stored. Some requests that end in an error (a trace that does not exist, an ingest request with an
> invalid span id) get `500` instead when they accept only YAML, and the collector log gets an `ERROR` with a stack trace
> (0.11.0 answered these two with `404` and `400`) — the same as a request that accepts only another format the server
> does not produce, such as `application/xml`. `/v3/api-docs.yaml` still answers `200`, as do `/v3/api-docs` and
> `/swagger-ui`. The agent and the web UI only use JSON and are not affected. Why: 0.10.0 made JSON bodies with a `null`
> number field or extra text after valid JSON fail with `400`, but YAML bodies stayed outside that change and were
> accepted with `202` (a `null` number was stored as 0); the unauthenticated ingest endpoint now takes JSON only.
> Changed: Gradle wrapper 8.14.6 → 9.9.1 and the shadow plugin 8.3.5 → 8.3.11 — the agent jar keeps the same classes and
> files as 0.11.0 except the two version entries (`agent-version.properties` and `Implementation-Version` in the
> manifest); the web UI is built with Node 24 (building from source is supported on Node 24 or later); server compiler
> warnings are cleaned up without behaviour changes; automated tests now cover double-encoded `..` paths without a token,
> the Spring Boot support-line warning around its end date, the log lines of a failed free-page reclaim and a busy WAL
> checkpoint, and no data loss when the nightly cleanup overlaps ingest; the security advisory table (`docs/security.md`)
> gets a check-time column per table. Expected: the agent version in the service list stays `0.11.0` until you redeploy
> the agent; the top-left label stays `v0.11`; each YAML request rejected with `415` or `406` leaves one `WARN` line in
> the collector log (the `500` above leaves an `ERROR` with a stack trace instead); every file inside the jars is dated
> 1980-02-01 and the agent jar is about 120 KB larger because the build tool packs jars differently. Upgrade: switch any
> YAML client to JSON, stop the collector, start `apilens-server-0.11.1.jar` and keep the agent as it is. If the collector
> uses an API key, pass the same key again the same way (`APILENS_AUTH_API_KEY` or `-Dapilens.auth.api-key`) when you
> restart it; without it the collector starts with authentication off and logs `API key not configured`. To roll back,
> swap the collector jar back to 0.11.0. JSON paths, fields and types are unchanged; only the answers to YAML requests
> (`415` · `406`, and `500` for some requests that end in an error) differ.
