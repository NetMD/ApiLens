## ApiLens v0.7.0 — 같은 내용을 한 번만 저장하기 | Store each body once

**collector(server) 만 바뀌는 릴리스입니다. agent 를 다시 배포할 필요가 없습니다.** 같은 요청·응답
본문이 저장소에 여러 번 담기던 것을 **한 번만 담고 나머지는 가리키게** 바꿨습니다. span 속성 안의
SQL 원문도 마찬가지입니다. 밖으로 나가는 응답과 화면에 보이는 값은 **이전과 같습니다** — 저장하는
방식만 바뀌었습니다.

⚠️ **이 버전은 기동할 때 DB 스키마를 바꾸고, 되돌리는 마이그레이션이 없습니다.** 올리기 전에
수집기를 정상 종료하고 **`apilens.db` 를 반드시 백업**하세요. 이전 상태로 돌아가는 길은 그 백업을
복원하는 것뿐입니다.

**This release changes only the collector (server) — you do not need to redeploy the agent.**
Request/response bodies that used to be stored again and again are now stored **once**, addressed by
a hash of their content; rows keep only the reference. The same is done for SQL statements embedded
in span attributes. API responses and everything you see on screen stay the same — only the storage
layout changed. ⚠️ **This release migrates the database on startup and there is no down-migration.**
Stop the collector and **back up `apilens.db` before upgrading**; restoring that backup is the only
way back.

---

### 새로운 기능 | What's new

- **같은 본문은 저장소 전체에서 한 번만 저장합니다** — 본문을 내용으로 만든 지문(SHA-256)으로
  식별해 **본문 자체는 별도 표에 한 번만** 두고, 기존 행은 그 지문만 갖습니다. 같은 내용이 다시
  들어오면 본문은 다시 저장되지 않습니다.
  - 지문은 **마스킹을 거치고 상한으로 자른 뒤의 저장 바이트**로 만듭니다. 마스킹 전 원문을 지문
    재료로 쓰거나 저장하는 경로는 없습니다.
  - 읽을 때 본문을 되돌려 붙이므로 **추적 상세 화면에 보이는 값은 이전과 같습니다.**

- **span 속성 안의 SQL 원문도 한 번만 저장합니다** — 같은 SQL 이 span 마다 통째로 들어가던 것을
  별도 표에 한 번만 두고, 속성에는 내부 참조만 남깁니다. 읽을 때 원문으로 되돌리므로 **응답의
  모양은 이전과 같습니다.**

- **아무 행도 안 가리키는 본문을 자동으로 치웁니다** — 밤 정리가 끝난 뒤와 「전체 지우기」 뒤에
  각각 한 번 돕니다. 몇 건을 지웠는지와 걸린 시간이 수집기 로그에 한 줄 남습니다(지운 것이 0 건이어도
  남습니다).

  ```
  payload body gc: deleted=1234 rounds=2 elapsedMs=87
  ```

  - **이 정리가 실패해도 뒷정리는 그대로 돕니다** — 정리 시각 기록·빈 공간 회수·WAL 줄이기는
    영향을 받지 않습니다. 실패는 로그 한 줄로 남고 **다음 밤이 이어서 지웁니다.** 긴급 대응
    대상이 아닙니다.
  - 한 번에 지우는 양에 상한이 있습니다. 상한에 닿으면 남은 것은 다음 실행이 이어 가고, 그
    사실도 로그 한 줄로 남습니다. **실패가 아닙니다.**

- **계측 분석 요약에 「고유 본문 합」 한 줄** — 조회한 구간 안에서 **같은 본문을 한 번만 센 바이트
  합**입니다. 옆에 있던 순위 표의 본문 용량은 **지금까지와 똑같이 참조당**으로 둡니다.
  - ⚠️ **두 값은 잣대가 다릅니다.** 순위 표는 "이 클래스가 만든 본문이 몇 바이트인가"이고, 이
    한 줄은 "그중 서로 다른 내용만 세면 몇 바이트인가"입니다. 빼거나 나누지 마세요.
  - **올린 뒤 약 이틀 동안은 이 값이 실제보다 크게 나옵니다** — 옛 형태 행은 행마다 별개 본문으로
    세기 때문입니다. 틀리는 방향은 **절감이 덜 되어 보이는 쪽**이고, 옛 형태 행이 사라지면 저절로
    정확해집니다.

- **수집기 로그에 외부에서 온 값이 그대로 찍히지 않습니다** — 인증 없이 열려 있는 적재 입구와 그
  예외 경로의 로그 인자를 감쌌습니다. 줄바꿈이 든 값이 들어와도 **로그가 한 줄로 유지**됩니다.
  로그 줄의 앞머리와 필드 이름은 **안 바꿨습니다** — 과거 로그와의 대조가 끊기지 않게 하기
  위해서입니다.

### 달라진 점 | Changed

- **올린 뒤 약 이틀 동안은 두 형태의 행이 섞여 있습니다** — 이미 쌓인 행은 **한 줄도 바꾸지
  않습니다**(옛 행을 새 형태로 옮기는 작업을 하지 않습니다). 두 형태를 모두 읽는 갈래가 들어 있어
  **화면에서는 구분 없이 똑같이** 보입니다. 옛 형태 행은 보관 기간이 지나면 평소처럼 사라지고,
  그때부터는 새 형태만 남습니다.
- **버전 0.6.3 → 0.7.0** (collector jar). 화면 버전 라벨은 `v0.6` → **`v0.7`**. **agent 버전은
  `0.6.0` 그대로**입니다 — 이번에도 agent 를 바꾸지 않았다는 뜻이며 정상입니다.
- **적재 트랜잭션은 쓰기로 시작합니다** — 밤 정리와 같은 순간에 겹쳐도 그 청크가 바로 버려지지
  않고 이전처럼 최대 10초를 기다립니다. (SQL 원문을 「이미 있는지 먼저 읽고」 넣는 순서였다면
  SQLite 가 기다리지 않고 바로 실패시킵니다 — 이 버전을 운영에 올린 첫 밤에 관측해 **출고 전에**
  고쳤습니다.)
- **본문 자동 정리 로그가 회전마다 한 줄 더 남습니다** — 커넥션 확보·문장·커밋에 걸린 시간(ms)을
  따로 적습니다. 위 요약 줄의 문면은 그대로입니다.

  ```
  payload body gc start: batchSize=1000 maxRounds=50
  payload body gc round: round=0 deleted=1000 acquireMs=2 statementMs=17 commitMs=258
  payload body gc: deleted=8552 rounds=9 elapsedMs=1032
  ```

### 주의 | Notes

- **얼마나 줄어드는지는 「응답 내용이 얼마나 자주 바뀌는가」에 달려 있습니다.** 같은 내용이 반복해서
  들어오는 환경일수록 많이 줄고, 매번 다른 내용이 들어오는 환경에서는 거의 안 줄어듭니다.
  **이 릴리스는 줄어드는 비율을 약속하지 않습니다** — 각자의 환경에서 재 보셔야 합니다.
  - 참고로 **이 프로젝트의 운영 환경에서 측정 시**(2026-09-05 15:33 · 보관 기간 1일 · 폴링 응답이
    대부분인 환경), 저장된 본문 합은 1,265,753,375 B / 559,187 행이었고 **서로 다른 내용만 세면
    3,678,347 B** 였습니다. span 속성 안의 SQL 은 **인용 바이트 171,716,209 B 에 서로 다른 원문
    57 종(43,248 B)** 이었습니다.
  - **이 숫자는 그 시점에 쌓여 있던 데이터를 잰 것이지, 이 릴리스가 줄여 주는 양이 아닙니다.**
- **SQL 원문 표는 이번 버전에서 지우지 않습니다** — 서로 다른 SQL 의 **종류 수만큼만** 늘고 대개
  배포할 때만 늡니다. 다만 앱이 문자열을 이어 붙여 SQL 을 만들면(`IN (?,?,?)` 의 물음표 개수가
  매번 다른 형태 등) 종류가 계속 늘 수 있고, 그러면 이 표는 **자라기만 합니다.**
- **파일 크기가 그날 바로 줄지는 않습니다** — 줄어드는 것은 **새로 들어가는 양**입니다. 이미 쓴
  페이지는 밤 정리와 빈 공간 회수가 평소 속도로 돌려줍니다.

### 업그레이드 | Upgrade

1. **수집기를 정상 종료합니다.**
2. ⚠️ **`apilens.db` 를 백업합니다 — 이 단계를 건너뛰지 마세요.** 이 버전은 기동할 때 스키마를
   바꾸고 **되돌리는 마이그레이션이 없습니다.** 되돌리는 길은 이 백업을 복원하는 것뿐입니다.
   (`-wal` · `-shm` 파일이 남아 있으면 함께 복사하세요.) 여유 공간도 미리 확인하세요.
3. **collector jar 를 교체하고 재기동합니다.** 기동할 때 마이그레이션 두 개가 자동으로 적용되어
   **스키마 버전이 5 에서 7 로** 올라갑니다(본문 표 1개 · SQL 원문 표 1개 · `payloads` 에 열 1개).
4. **agent 는 그대로 두세요** — **다시 배포할 필요가 없고**, 대상 앱 JVM 재시작도 필요 없습니다.
   agent 버전 라벨이 `0.6.0` 으로 계속 보이는 것이 정상입니다.
5. **새 설정 항목이 없습니다** — 설정 파일이나 JVM 옵션을 손댈 필요가 없습니다.

- **되돌릴 때**: jar 만 이전 버전으로 바꾸지 마세요. 이 버전이 저장한 본문과 SQL 원문은 이전 jar 가
  읽는 자리에 없어서 **오류가 나는 것이 아니라 조용히 빈 값**으로 보이고, 새 표에 쌓인 본문도 이전
  jar 는 지우지 않습니다. **되돌릴 때는 jar 와 백업을 함께 되돌리세요.**
- **API 호환** — 경로·요청·응답에서 삭제되거나 타입이 바뀐 필드가 **0**이고 새 endpoint 도
  **0**입니다. 계측 분석 응답의 요약에 필드 하나가 **맨 뒤에 추가**됐을 뿐입니다. 추적 상세의
  SQL 과 본문 필드는 **문자열 그대로** 나갑니다.

> **Collector-only release — no agent redeploy needed.** Bodies are now content-addressed: each
> distinct body is stored once in its own table and payload rows keep a SHA-256 reference. The
> hash is taken **after** masking and truncation, so nothing unmasked is ever hashed or stored.
> SQL statements embedded in span attributes are interned the same way and restored on read, so
> **API responses are unchanged field-for-field** — the only addition is one trailing field in the
> instrument analysis summary. Rows that no body references any more are
> swept after the nightly cleanup and after a full purge; that sweep is isolated — if it fails, the
> rest of the maintenance still runs and the next night picks up where it stopped, and each sweep
> round now logs its own timing line. The instrument
> analysis summary gained one line, "고유 본문 합" (distinct-body bytes in the selected window);
> the per-reference bytes in the ranking table are unchanged, and the two are **not** on the same
> scale. Log arguments coming from the unauthenticated ingest path are now sanitised so a newline
> in incoming data can no longer split a log line; log prefixes and field names are untouched.
> Ingest transactions start with a write, so a chunk that collides with the nightly cleanup waits
> (up to 10 s) instead of being dropped at once — found on the first production night and fixed
> before release.
> ⚠️ **This release migrates the schema on startup (5 → 7) and ships no down-migration. Back up
> `apilens.db` first — restoring that backup is the only way back.** Existing rows are **not**
> rewritten; both old- and new-form rows are read for about two days until the old ones age out,
> and they look identical on screen. During that window the "고유 본문 합" line reads higher than
> reality (it errs on the safe side). How much you actually save depends on **how often your
> response bodies change** — this release promises no percentage. The SQL statement table is not
> garbage-collected in this version: it grows with the number of distinct statements only, but it
> only ever grows.
