## ApiLens v0.11.2 — JSON 을 받지 않는 요청은 처리 전에 406 · 지문 32자 · 보안 판올림 | Requests that refuse JSON end with 406 before processing · 32-character fingerprints · security updates

**collector(server) jar 만 바꾸면 되는 정비 릴리스입니다. agent 코드는 바뀌지 않아 다시 배포하지 않아도 됩니다** —
0.11.1 agent 를 그대로 쓰면 됩니다. **응답을 JSON 으로 받지 않겠다는 요청은 이제 처리하기 전에 `406` 으로 끝나고,
데이터나 설정을 바꾸는 요청도 반영되지 않습니다**(0.11.1 은 처리한 뒤 `406` 이었습니다 — 아래 참고). agent 와 화면은
해당하지 않고, **`Accept` 머리를 손으로 적어 API 를 부르는 스크립트 · 도구만** 확인하면 됩니다.
그 밖에 같은 본문 · SQL 원문을 한 번만 담는 지문을 32자로 줄이고(옛 64자 행은 그대로 함께 읽힘), Spring Boot 4.1.3 ·
sqlite-jdbc 3.54.1.0 으로 올려 공지된 취약점의 고침판 위로 맞추고, 보안 공지 대조표를 다시 맞췄습니다.

**DB 스키마는 바뀌지 않습니다** — 마이그레이션이 없어, 되돌리려면 0.11.1 jar 로 바꾸기만 하면 됩니다. 백업을 복원할
필요가 없습니다. 화면 왼쪽 위 버전 라벨은 **`v0.11` 그대로**입니다 — 판은 `/v3/api-docs` 의 `info.version`(`0.11.2`)으로
확인하세요.

**A maintenance release — replace only the collector (server) jar. The agent code is unchanged, so you can keep using
the 0.11.1 agent.** A request that does not accept a JSON reply now **ends with `406` before it is processed**, so a
request that changes data or settings has no effect (0.11.1 answered `406` after processing — see below). The agent and
the web UI are not affected; only scripts or tools that write their own `Accept` header need a check. New fingerprints
are 32 characters (existing 64-character rows stay and are read as is), Spring Boot moves to 4.1.3 and sqlite-jdbc to
3.54.1.0, and the security advisory table is refreshed. **No database migration** — rolling back is just swapping the jar.
The version label in the top-left corner **stays `v0.11`**; check `info.version` (`0.11.2`) in `/v3/api-docs`.

### JSON 을 받지 않는 요청은 처리 전에 406 | Breaking change: requests that refuse JSON

- **어떤 요청이 `406` 을 받나** — `Accept` 의 항목 가운데 JSON(`application/json` · `application/*+json`)을 받는 것이
  하나도 없는 요청입니다.
  - `Accept` 가 없거나 `*/*` 를 담은 요청은 JSON 을 받는 것으로 봅니다. 다만 그 항목에 `q=0`(받지 않음)을 붙였거나,
    응답에 쓸 수 없는 문자셋(예: `ISO-8859-1` · `US-ASCII`)만 허락했으면 받지 않는 것으로 봅니다.
  - API 키를 켠 수집기에서 토큰이 없는 요청은 그보다 먼저 `401` 을 받습니다.
- **0.11.1 과 다른 점**
  - YAML 로만 받겠다는 요청(`Accept: application/yaml`)은 0.11.1 에서 처리한 **뒤** `406` 을 받아, 바꾸는 요청은 `406` 을
    받아도 이미 반영돼 있었습니다. 0.11.2 는 처리하기 **전**에 끝내므로 반영되지 않습니다. 결과가 필요하면 JSON 으로
    다시 보내세요.
  - JSON 을 `q=0` 으로 적은 요청(예: `Accept: application/json;q=0`)은 0.11.1 에서 그대로 처리됐습니다(바꾸는 요청도
    반영). 이제 `406` 이고 반영되지 않습니다.
  - `Accept: application/json;charset=US-ASCII` · `*/*;charset=ISO-8859-1` 은 0.11.1 에서 `200` 이었고 이제 `406` 입니다.
    `application/json;charset=ISO-8859-1` 은 0.11.1 에서도 `406` 이었지만 처리한 뒤였고, 이제는 처리 전입니다.
  - `GET /v1/setup/agent-jar` 를 `Accept: application/json` 하나만 적어 부르면 0.11.1 은 jar 를 `200` 으로 내려 줬고,
    이제 `406` 입니다. 브라우저 · agent · `curl` 기본값(`*/*`) · `Accept` 없음 · `application/octet-stream` 은 그대로
    `200` 입니다.
  - 0.11.1 이 적었던 「YAML 로만 받겠다고 한 오류 요청의 `500`」(없는 trace 조회 · 잘못된 span id 를 담은 수집 요청
    등)은 이제 처리 전 `406` 입니다. `Accept` 와 무관한 `500` 은 그대로입니다.
- **`406` 응답 본문** — 요청한 형식에 따라 셋 중 하나입니다. 비어 있음(YAML · XML · 쓸 수 없는 문자셋 등) · 서버 기본
  HTML 오류 쪽지(`text/html`) · 서버 기본 오류 JSON(`timestamp` · `status` · `error` · `path` — `q=0` · `*/*;q=0` ·
  `US-ASCII` 처럼 JSON 으로 쓸 수는 있는 경우). 어느 쪽도 이 API 의 `{"error": …}` 꼴이 아닙니다.
- **누가 영향을 받나** — `Accept` 머리를 손으로 적어 API 를 부르는 스크립트 · 도구뿐입니다. agent 는 `Accept` 를 보내지
  않고 화면은 `application/json` 을 보냅니다.
- **왜 바꿨나** — 0.11.1 은 `406` 을 처리한 뒤에 냈기 때문에, 바꾸는 요청을 보낸 쪽이 실패로 읽고 다시 보내면 같은
  변경이 한 번 더 일어날 수 있었습니다. 이제 `406` 은 「아무것도 하지 않았다」는 뜻입니다.

### 바뀐 것 | Changed

- **지문 길이 64자 → 32자** — 같은 payload 본문과 같은 SQL 원문을 한 번만 담을 때 쓰는 지문(`body_hash` ·
  `stmt_hash` · span 속성 `apilens.stmt.ref`)을 새로 쓸 때 16진수 32자로 씁니다.
  - 0.11.1 까지 쓴 64자 행은 그대로 두고 함께 읽습니다. 두 길이는 보관 기간 동안 함께 있다가, 옛 행이 보관 기간을
    넘겨 정리되면 사라집니다.
  - DB 스키마와 마이그레이션은 그대로입니다. DB 를 직접 읽는 스크립트가 지문 길이를 64 로 가정했다면 고치세요.
- **0.11.1 로 되돌려도 읽힙니다** — 0.11.1 jar 는 32자 행도 글자 그대로 읽습니다. 되돌린 뒤 새로 쓰는 행은 다시
  64자이고, 0.11.2 로 다시 올리면 두 길이가 한 번 더 함께 있게 됩니다. DB 를 손볼 필요도, 백업을 복원할 필요도
  없습니다.
- **의존성 판올림** — Spring Boot 4.1.2 → 4.1.3(Spring Framework 7.0.10 → 7.0.11 · Jackson 3 3.1.7 → 3.1.8 ·
  Jackson 2 2.21.7 → 2.21.8 · Hibernate 7.4.13 → 7.4.15 등) · sqlite-jdbc 3.53.4.0 → 3.54.1.0(SQLite 3.53.4 → 3.54.1).
  Tomcat 11.0.27 · Flyway 12.4.0 · logback 1.5.38 과 agent 안의 Jackson 2.18.12 는 그대로입니다.
- 문서: 보안 공지 대조표(`docs/security.md`)를 v0.11.2 판으로 다시 맞췄습니다(새 공지 40행 · 「확인한 목록」 줄).
  README 「현재 한계」에 Java4Shell 항목을 더했습니다. `-D` 로 준 API 키가 `ps` 로 보인다는 주의를 README ·
  `docs/setup.md` · `docs/api.md` 에 더했습니다. `docs/api.md` 에 처리 전 `406` · 지문 길이 · agent jar 내려받기 응답
  줄을 더했습니다.
- **버전 0.11.1 → 0.11.2** (collector jar · agent jar).

### 보안 | Security

- 이번 판올림으로 Spring Framework · Spring Boot 공지 13건, Jackson 공지 1건(CVE-2026-110879), SQLite 공지 10건의
  고침판 위로 올라갔습니다. 공지별 영향 범위 · 고침판 · 이 제품에서의 성립 조건은
  [`docs/security.md`](https://github.com/NetMD/ApiLens/blob/main/docs/security.md) 에 있습니다.
- **Tomcat 11.0.27 은 그대로입니다** — 공지 10건이 이 판을 범위에 넣지만(고침판 11.0.29), 성립 조건(HTTP/2 · WebSocket
  · 클러스터 · CGI · 몇몇 밸브와 필터 등)이 이 제품에 없습니다. logback 공지 2건 · jackson-dataformat-yaml 공지 1건도
  판은 범위 안이지만 성립 조건이 없습니다. 이 셋은 지난 대조표에서 빠져 있던 것을 이번에 더했습니다.
- **수집기를 x86-64(AVX-512) 서버에서 띄울 때는 고침판 JDK 를 쓰세요** — Java4Shell(CVE-2026-114938)이 고쳐지지 않은
  JDK 에서는 요청의 `cursor` 값이 JDK Base64 디코더로 바로 들어갑니다. 고침판은 Oracle 공지에 적힌 판입니다. arm64
  서버는 해당하지 않습니다. 수집기를 띄우는 JDK 는 설치하는 쪽이 고르므로, 이 판을 올려서 고쳐지는 것이 아닙니다.

### 이렇게 보여도 정상 | Looks odd, but expected

- **서비스 목록의 agent 버전이 `0.11.1` 로 보입니다.** agent 를 다시 배포하지 않았다는 뜻이고 정상입니다.
- **화면 왼쪽 위 라벨이 `v0.11` 그대로입니다.** 라벨은 앞 두 자리만 표시합니다. 판은 `/v3/api-docs` 의
  `info.version` 이 정확합니다.
- **`406` 마다 수집기 로그에 `WARN` 한 줄이 남습니다** — `HttpMediaTypeNotAcceptableException: No acceptable
  representation` 을 적은 줄입니다. 요청 하나에 한 줄이고, 그 요청은 처리되지 않았습니다.
- **두 길이의 지문이 함께 있는 동안** 같은 본문이 길이마다 한 벌씩 저장될 수 있어 저장량이 잠시 늘고, 계측 분석의
  고유 본문 수가 커 보일 수 있습니다. 옛 행이 정리되면 돌아옵니다.

### 업그레이드 | Upgrade

1. **`Accept` 머리를 손으로 적어 API 를 부르는 스크립트 · 도구가 있으면 확인합니다** — JSON 을 받는다고 적었는지,
   `q=0` 이나 다른 문자셋을 붙이지 않았는지 봅니다. agent 와 화면만 쓰는 설치는 할 일이 없습니다.
2. **수집기를 x86-64(AVX-512) 서버에서 띄운다면 JDK 가 Oracle 2026-11 공지의 고침판인지 확인합니다.** arm64 서버는
   해당하지 않습니다.
3. **수집기를 정상 종료합니다.**
4. **collector jar 를 `apilens-server-0.11.2.jar` 로 바꾸고 다시 띄웁니다.** 이 버전은 **DB 스키마를 바꾸지 않습니다**.
   API 키를 켜 둔 수집기는 다시 띄울 때도 같은 키를 넘기세요 — 환경 변수 `APILENS_AUTH_API_KEY` 를 권합니다.
   `-Dapilens.auth.api-key` 로 넘긴 키는 같은 서버의 다른 사용자가 `ps` 로 볼 수 있습니다. 키를 넘기지 않으면 인증이
   꺼진 채 뜹니다. 기동 로그에 `API key not configured` 경고가 있으면 키가 빠진 것입니다.
5. **agent 는 그대로 둡니다** — 0.11.1 agent 를 그대로 쓰면 되고, 대상 앱을 재시작할 필요도 없습니다. 서비스 목록의
   agent 버전 라벨을 `0.11.2` 로 맞추고 싶을 때만, collector 가 떠 있는 것을 확인한 뒤 새 agent jar 로 바꾸고 대상
   앱을 재시작하세요.
6. **열려 있던 브라우저 탭은 새로고침하세요.**
7. **새 설정 항목이 없습니다** — 설정 파일이나 JVM 옵션을 손댈 필요가 없습니다.

- **되돌릴 때**: **collector jar 만 0.11.1 로 바꾸면 됩니다.** 0.11.1 은 32자 지문 행도 그대로 읽습니다. 스키마가
  그대로라 백업을 복원할 필요가 없습니다.
- **API 모양** — JSON 요청 · 응답의 경로와 필드 이름 · 타입은 그대로입니다. 달라진 것은 `Accept` 가 JSON 을 받지 않는
  요청 · agent jar 를 JSON 으로만 받겠다는 요청에 대한 응답(처리 전 `406`)입니다.

> **Collector-only maintenance release — keep the 0.11.1 agent, no database migration.** Breaking change for clients
> that write their own `Accept` header: a request with no `Accept` entry that takes JSON (`application/json` or
> `application/*+json`) now ends with `406` **before it is processed**, so a request that changes data or settings has no
> effect. A missing `Accept` or one that contains `*/*` counts as taking JSON, unless that entry carries `q=0` or allows
> only a charset the reply cannot be written in (for example `ISO-8859-1` or `US-ASCII`). With an API key configured, a
> request without a token still gets `401` first. Compared with 0.11.1: a YAML-only `Accept` used to get `406` after the
> request was carried out (changes were already applied) and now gets it before; `Accept: application/json;q=0` used to
> be processed and now gets `406`; `application/json;charset=US-ASCII` and `*/*;charset=ISO-8859-1` used to get `200` and
> now get `406`; `application/json;charset=ISO-8859-1` got `406` after processing and now before; `GET
> /v1/setup/agent-jar` with only `Accept: application/json` used to return the jar with `200` and now gets `406` (browsers,
> the agent, curl's default `*/*`, no `Accept` and `application/octet-stream` still get `200`); and the `500` that 0.11.1
> listed for YAML-only error requests (a trace that does not exist, an ingest request with an invalid span id) is now a
> `406` before processing — `500`s unrelated to `Accept` are unchanged. The `406` body is empty (YAML, XML, an unusable
> charset), the server's default HTML error page (`text/html`), or the server's default error JSON (`timestamp`,
> `status`, `error`, `path`) when JSON can still be written (`q=0`, `*/*;q=0`, `US-ASCII`) — never this API's
> `{"error": …}` shape. Why: 0.11.1 sent `406` after processing, so a caller that read it as a failure and retried could
> apply the same change twice; a `406` now means nothing was done. Changed: new fingerprints (`body_hash`, `stmt_hash`,
> the `apilens.stmt.ref` span attribute) are 32 hex characters; 64-character rows written by 0.11.1 and earlier stay and
> are read as is, both lengths coexist for the retention period, and the schema is unchanged — fix any script that reads
> the database directly and assumes 64 characters; rolling back to 0.11.1 also reads the 32-character rows, rows written
> after the rollback are 64 characters again, and no database work or backup restore is needed. Spring Boot 4.1.2 → 4.1.3
> (Spring Framework 7.0.11, Jackson 3.1.8 and 2.21.8, Hibernate 7.4.15) and sqlite-jdbc 3.53.4.0 → 3.54.1.0 (SQLite
> 3.54.1); Tomcat 11.0.27, Flyway 12.4.0, logback 1.5.38 and the agent's Jackson 2.18.12 are unchanged. Security: the
> update moves past the fixed versions of 13 Spring Framework and Spring Boot advisories, one Jackson advisory
> (CVE-2026-110879) and 10 SQLite advisories; 10 Tomcat advisories, two logback advisories and one jackson-dataformat-yaml
> advisory include the shipped versions but their conditions do not exist in this product (the last three were missing
> from the previous table). On x86-64 (AVX-512) hosts, run the collector on a patched JDK (the fixed version in Oracle's
> advisory or later) because of Java4Shell (CVE-2026-114938) — on an unpatched JDK the request's `cursor` value goes
> straight into the JDK Base64 decoder; arm64 hosts are not affected, and this release cannot fix the JDK you install.
> Expected: the agent version in the service list stays `0.11.1` until you redeploy the agent; the top-left label stays
> `v0.11`; each `406` leaves one `WARN` line (`HttpMediaTypeNotAcceptableException: No acceptable representation`) and the
> request was not processed; while both fingerprint lengths coexist the same body may be stored once per length, so
> storage grows for a while and the unique-body count in the instrumentation analysis can look larger. Upgrade: check any
> client that writes its own `Accept`, check the JDK on x86-64 (AVX-512) hosts, stop the collector, start
> `apilens-server-0.11.2.jar` and keep the agent as it is. If the collector uses an API key, pass the same key again —
> the environment variable `APILENS_AUTH_API_KEY` is recommended because a key passed with `-Dapilens.auth.api-key` is
> visible to other users on the same host via `ps`; without a key the collector starts with authentication off and logs
> `API key not configured`. To roll back, swap the collector jar back to 0.11.1. JSON paths, fields and types are
> unchanged; only the answer to requests whose `Accept` takes no JSON differs.
