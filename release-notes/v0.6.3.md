## ApiLens v0.6.3 — 끊긴 구간 되짚기 + 검사망을 출고 경로에 맞추기 | Trace the gap, align CI with the release path

**collector(server) 만 바뀌는 릴리스입니다. agent 를 다시 배포할 필요가 없습니다.** 수집이
한동안 끊겼다가 다시 들어오면 **그 구간을 수집기 로그에 한 줄로 남깁니다** — 언제부터 언제까지
안 들어왔는지를 나중에 되짚을 수 있습니다. 그리고 저장소의 평소 검사망이 **실제 출고 때와 같은
명령으로** 돌도록 맞췄습니다. 지금까지는 태그를 밀고 나서야 처음 보이는 문제가 있었습니다.
**DB 스키마 변경이 없으므로** collector jar 만 교체하고 재기동하면 됩니다.

**This release changes only the collector (server) — you do not need to redeploy the agent.**
When ingest stops for a while and then resumes, the collector writes a single log line
describing the gap, so you can reconstruct the outage afterwards. The everyday CI pipeline now
builds with the same command as the release pipeline and fails when the web assets are missing
from the jar. **No schema migration** — just replace the collector jar and restart.

---

### 새로운 기능 | What's new

- **끊겼다 이어진 구간을 로그 한 줄로** — 수집이 한동안 없다가 다시 들어오면 수집기 로그에
  `ingest resumed:` 로 시작하는 한 줄이 남습니다. 직전에 마지막으로 받은 시각, 그 사이 공백
  (밀리초), 서비스 이름이 함께 적힙니다.

  ```
  ingest resumed: lastSeenBefore=2026-01-02T03:04:05 gapMs=345600001 (4.00d) service=my-app
  ```

  - ⚠️ **이것은 나중에 되짚기 위한 기록이지, 무슨 일이 나면 알려 주는 장치가 아닙니다.**
    수집기가 아예 꺼져 있던 구간은 **다시 켜진 뒤에야** 이 줄로 드러납니다. 꺼져 있는 동안에는
    아무 데도 안 뜹니다 — 그 표시를 만들어 주는 것이 바로 그 프로그램이기 때문입니다.
    **이 릴리스는 그 부분을 못 닫습니다.**
  - 공백이 짧으면(10분 미만) 줄이 안 남습니다. 처음 등록된 서비스에도 남지 않습니다 —
    견줄 직전 값이 없기 때문입니다. **둘 다 정상입니다.**
  - 괄호 안의 `(4.00d)` 는 자릿수를 눈으로 가늠하라고 덧붙인 것입니다. 값으로 계산할 때는
    `gapMs` 를 쓰세요.
  - 줄 앞머리 `ingest resumed:` 는 앞으로도 고정입니다. 새 항목이 생기면 뒤에만 붙습니다 —
    과거 로그와의 대조가 끊기지 않게 하기 위해서입니다.
  - 이 조회가 어떤 이유로든 실패해도 **수신은 그대로 진행됩니다.** 그때는 실패했다는 사실만
    로그에 한 줄 남습니다.

### 달라진 점 | Changed

- **평소 검사망이 출고 때와 같은 명령으로 돕니다** — 저장소의 자동 검사가 화면 빌드 결과를
  이어받아 **출고와 같은 명령으로** 빌드하고, 화면 자원이 jar 안에 안 들어가면 **경고가 아니라
  실패**로 잡습니다. 화면 문법 검사·화면 시험·화면 빌드도 이제 실패하면 검사망이 빨개집니다
  (전에는 실패해도 통과 처리됐습니다).
  - **내려받아 쓰는 분에게 제품 동작이 달라지는 것은 없습니다.** 같은 코드가 평소 검사는
    통과하고 출고에서만 깨지던 구조를 없앤 것입니다.
- **회수 가능한 빈 공간 값을 자동 시험이 실제로 대조합니다** — 이 값을 확인하던 시험이 빈 공간이
  0 인 상태만 보고 있어서, 값이 잘못 계산돼도 그대로 통과했습니다. 이제 빈 페이지를 실제로 만든
  뒤 대조하고, 옆의 DB 크기 값도 함께 봅니다. **제품 동작은 이전과 같습니다** — 앞으로 이 값이
  잘못되면 소리가 나게 만든 것입니다.

### 주의 | Notes

- **보관 기간 야간 정리(오래된 기록을 지우는 배치 루프)가 한 번에 다 못 지우고 끝나는 경로는
  정상 경로에 없습니다** — 코드를 읽어 확인했고, 관측된 정리는 전부 마지막 묶음이 묶음 크기보다
  작았습니다(대상이 바닥났다는 뜻입니다). 다만 **같은 시각에 도는 고아 기록 스윕은 여기에
  해당하지 않습니다** — 그쪽은 한 번에 살펴보는 후보 수에 상한이 있어 한 밤에 다 안 끝나는 것이
  정상입니다.
  그리고 이 판정에는 전제가 하나 더 있습니다 — **정리가 도는 동안 수집기 프로세스가 살아 있어야 하고**,
  정리 중에 예외가 나지 않아야 합니다. 그 전제가 깨지는 빈도는 재지 않았습니다.
- **어느 날 정리가 지운 양이 앞뒤 날과 크게 벌어진 사례를 한 번 관측했고, 원인은 아직 못
  밝혔습니다.** 설명을 두 가지 세웠다가 둘 다 기각했습니다 — 하나는 코드로(끊겼다 이어질 때
  밀린 전송이 한꺼번에 오는 구조가 아닙니다), 하나는 산술로(들어오는 양의 하루 굴곡으로는
  일부만 설명됩니다). **"설명됐다" 나 "정상이다" 로 적지 않습니다.** 위 새 로그 줄이 몇 주
  쌓여야 답을 볼 수 있습니다.

### 업그레이드 | Upgrade

- **collector(server) jar 만 교체하고 재기동하면 됩니다.** **agent 를 다시 배포할 필요가 없고**,
  대상 앱 JVM 재시작도 필요 없습니다.
- **DB 스키마 변경이 없습니다** — 마이그레이션이 실행되지 않으므로 되돌릴 수 없는 변경도 없습니다.
  DB 파일은 그대로입니다.
- **API 호환** — 경로·요청·응답의 필드 구성이 그대로입니다(추가·삭제·타입 변경 0). 새 endpoint 도
  없고, 화면도 바뀌지 않습니다.
- **새 설정 항목이 없습니다** — 설정 파일이나 JVM 옵션을 손댈 필요가 없습니다.
- **agent 버전 라벨은 `0.6.0` 으로 계속 보입니다.** 이번에도 agent 를 바꾸지 않았다는 뜻이며
  정상입니다.

> **Collector-only release — no agent redeploy needed.** Replace the collector jar and restart.
> **No schema migration**, so nothing irreversible happens on startup. API contracts are
> unchanged field-for-field and the UI is untouched. The collector now writes one
> `ingest resumed:` line when ingest resumes after a gap of ten minutes or more, carrying the
> previous last-seen timestamp, the gap in milliseconds and the service name. ⚠️ **This is an
> after-the-fact record, not an alerting mechanism** — a window in which the collector process
> itself was gone only surfaces once it comes back, because the process that would report it is
> the one that was missing. **This release does not close that gap.** No line is written for
> gaps under ten minutes or for a service seen for the first time; both are expected. On the
> repository side, CI now builds with the same command as the release pipeline and fails (rather
> than warns) when the web assets are missing from the jar; the frontend lint, tests and build
> are no longer silently passed. None of that changes runtime behaviour for users. The agent
> version label keeps showing `0.6.0` — that is expected, because the agent did not change.
