## ApiLens v0.6.2 — 사라지던 흐름 되살리기 + 상태를 보이게 | Stop losing flows, make state visible

**collector(server) 만 바뀌는 릴리스입니다. agent 를 다시 배포할 필요가 없습니다.** 적재의
마지막 단계에서 흐름 요약을 저장할 때 **읽는 사이에 다른 저장이 끼어들면 그 자리에서
실패**하던 구조를 없앴습니다. 그렇게 되면 기록은 저장됐는데 요약 행이 없어 **그 흐름이 화면
목록에 아예 안 나왔습니다.** 그리고 그런 일이 얼마나 있었는지, DB 가 지금 얼마나 큰지를
버튼을 누르지 않아도 볼 수 있게 했습니다. 고아 기록 정리의 실행 시각은 보관 기간 정리와
**따로 설정**하도록 나눴습니다(기본값은 그대로 매일 04:00).
**DB 스키마 변경이 없으므로** collector jar 만 교체하고 재기동하면 됩니다.

**This release changes only the collector (server) — you do not need to redeploy the agent.**
When a flow's summary row was written, the read-then-write sequence could fail immediately if
another write landed in between; the spans were stored but the summary row was not, so the
whole flow never appeared in the list. That failure path is now gone. The settings page also
shows, without pressing any button, how many summaries were deferred and how large the
database is. Orphan-record cleanup now has its **own schedule setting** (same 04:00 default).
**No schema migration** — just replace the collector jar and restart.

---

### 고친 것 | Fixed

- **흐름이 통째로 화면에서 사라지던 문제** — 적재는 기록(span)을 먼저 저장하고 마지막에 그 흐름의
  **요약 행 한 개**를 씁니다. 그 요약 작업이 **먼저 읽고 나중에 쓰는 하나의 묶음**이라, 읽는 사이에
  다른 저장이 끼어들면 쓰기가 **기다리지도 않고 그 자리에서 실패**했습니다.
  - 그러면 기록은 남았는데 요약 행이 없어, 그 흐름이 **목록에 아예 안 나오고** 기록만 떠돌았습니다.
    화면에는 아무 표시도 안 났습니다.
  - 이제 요약 저장을 **묶음 밖에서** 합니다 — 실패하던 그 경로 자체가 없어집니다.
  - ⚠️ **얼마나 줄어드는지 이 노트는 숫자로 적지 않습니다.** 이번에 만든 것은 그것을 **재는 자**이고
    (아래 「새로운 기능」), 실제 값은 다음 버전이 이 계기로 잽니다. 안 잰 것을 잰 것처럼 적지 않습니다.
- **요약 저장이 실패했을 때 원인을 알 수 있게** — 서버 로그에 이전에는 감싸고 있는 클래스 이름만
  찍혀서 원인을 가를 수 없었습니다. 이제 **근본 원인 문자열**이 함께 남습니다. 로그 줄의 앞머리는
  그대로라 과거 로그와의 대조가 끊기지 않습니다.

### 새로운 기능 | What's new

- **요약 저장 실패 누계 표시** — 설정 페이지 「적재 상태」에 **요약을 저장하지 못한 흐름 수**가 함께
  보입니다.
  - 이 값이 0 이 아니면 그 사이에 **흐름이 화면에서 사라진 적이 있다**는 뜻이라, 옆의 `(정상)` 표시가
    붙지 않습니다. 지금까지는 이런 일이 나도 화면이 계속 `(정상)` 이라고 말했습니다.
  - 서버 메모리에만 있는 값이라 **재시작하면 0 부터 다시 셉니다** — 재시작 후 0 은 정상입니다.
- **DB 크기·회수 가능한 빈 공간 상시 표시** — 버튼을 누르지 않아도 설정 페이지에서 **DB 파일 크기**와
  **회수 가능한 빈 공간**을 볼 수 있습니다. 지금까지는 [지난 데이터 정리] 같은 버튼을 눌러야만
  나왔습니다.
  - ⚠️ 두 값은 조회 시점에 DB 헤더에서 읽습니다. **읽기에 실패하면 두 값만 `0 B` 로 내려가고**
    일시정지·재개 같은 조작 자체는 그대로 적용됩니다(서버 로그에 경고 1줄). `0 B` 가 보이면
    서버 로그를 함께 보세요.
  - 「회수 가능한 빈 공간」이 `0 B` 인 것은 **결함이 아닙니다** — 회수할 것이 없다는 뜻입니다.
- **야간 정리 시작 로그에 DB 크기 정보 추가** — 밤마다 정리를 시작할 때 페이지 수와 페이지 크기를
  함께 남깁니다. 다음 버전이 "무엇을 줄였더니 얼마나 줄었는지" 를 되돌아볼 수 있게 하는 기록입니다.
  화면 표시를 대체하는 것이 아닙니다 — 화면은 지금 상태를 보는 자리, 로그는 나중에 되돌아볼 자리입니다.

### 달라진 점 | Changed

- **고아 기록 정리의 실행 시각을 따로 설정합니다** — 어느 흐름에도 붙지 못한 기록을 치우는 야간
  정리가, 보관 기간 정리와 **별개의 시각 설정**(`apilens.retention.orphan-sweep-cron`)으로 돕니다.
  **기본값은 둘 다 지금과 같은 매일 04:00 이라 동작은 그대로입니다.**
  - **왜 나눴나**: 이 정리는 "첫 밤에 후보로 적고, 다음 밤에도 여전히 고아인 것만 지운다" 는 유예를
    둡니다. 그 「밤」이 보관 기간 정리 주기에 묶여 있어서, 정리 주기를 짧게 바꾸면 **유예도 함께
    짧아지는데 그 사실이 어디에도 안 적혀 있었습니다.**
  - ⚠️ **유예가 시간 기반이 된 것은 아닙니다.** 유예는 여전히 "정리가 도는 횟수" 기준이라, 새로 생긴
    이 시각 설정 자체를 짧게 바꾸면 유예는 똑같이 짧아집니다. 달라진 것은 ① 보관 기간 주기만
    바꿔서는 안 짧아진다 ② 설정 이름이 무엇을 지배하는지 말한다 ③ 정리 사이 간격이 서버 로그에
    남는다 — 이 셋입니다.
  - 수동 [지난 데이터 정리] 가 고아 기록을 건드리지 않는 것도, [전체 삭제] 만 유예 없이 함께 지우는
    것도 **그대로**입니다.

### 문서 | Docs

- **`docs/api.md` 「밀린 빈 공간을 한 번에 돌려받기」 절 재구성** — 화면의 **[디스크 조각 정리(최적화)]
  버튼을 먼저 시도**하도록 안내를 앞에 뒀습니다. 사유는 두 가지 구조적 차이입니다 — 버튼 경로는
  디스크 여유가 모자라면 **스스로 거부하거나 부분 실패를 알리고**, **수집기를 멈추지 않아도** 됩니다.
  기존 셸 절차는 **지우지 않고 대안으로 뒤에 그대로** 뒀습니다(명령·경고 문장 무변경).
  두 경로의 회수량·소요는 쌓인 양에 달려 있어 이 문서가 견주지 않습니다.
- **1단계 셸 조회를 화면 값으로 대신할 수 있습니다** — 「회수 가능한 빈 공간」이 그 값입니다.
- **회수 어림값의 한계 문장 추가** — "빈 페이지 1,000개당 10~20 MB" 어림값은 안내한 명령처럼 **한 문장으로
  한 번에 실행할 때는 실제보다 크게 잡는 쪽**이었습니다. 여유를 과하게 요구하는 쪽이라 안전한
  방향이고, **값은 그대로** 뒀습니다.
- **README** — 기능 표에 행 3개, 「현재 한계」에 항목 2개를 **추가만** 했습니다.

### 업그레이드 | Upgrade

- **collector(server) jar 만 교체하고 재기동하면 됩니다.** **agent 를 다시 배포할 필요가 없고**, 대상 앱
  JVM 재시작도 필요 없습니다.
- **DB 스키마 변경이 없습니다** — 마이그레이션이 실행되지 않으므로 되돌릴 수 없는 변경도 없습니다.
- **API 호환** — 유지보수 상태 응답(`/v1/maintenance/{status,pause,resume}`)에 **필드 세 개가 뒤에
  추가**됩니다(`traceSummaryDeferred` · `dbSizeBytes` · `freePageBytes`). 기존 필드의 이름·타입·순서·의미는
  그대로이고 삭제·타입 변경은 없습니다. 다른 경로의 요청·응답은 변화 없습니다.
- **설정 파일** — `apilens.retention.orphan-sweep-cron` 이 새로 생겼습니다. **적지 않아도 기본값
  (매일 04:00)으로 돕니다** — 지금 동작과 같으므로 손댈 필요가 없습니다.
- **agent 버전 라벨은 `0.6.0` 으로 계속 보입니다.** 이번에도 agent 를 바꾸지 않았다는 뜻이며 정상입니다.

> **Collector-only release — no agent redeploy needed.** Replace the collector jar and
> restart. **No schema migration**, so nothing irreversible happens on startup. The main fix:
> writing a flow's summary row no longer runs inside a read-then-write transaction, so the
> immediate write-upgrade failure that silently dropped whole flows from the list is gone.
> This note deliberately publishes **no percentage for how much that reduces** — this release
> builds the instrument, and the next one reads it. The settings page now shows the deferred
> summary count plus **database size and reclaimable free space** without pressing a button;
> if those two read `0 B`, check the server log (an observation failure falls back to zero
> without affecting pause/resume). Orphan-record cleanup gained its **own schedule key**
> (`apilens.retention.orphan-sweep-cron`, same 04:00 default) — the grace period is still
> counted in cleanup runs, not in hours. The status response gains **three additive fields**;
> existing fields are unchanged. The agent version label keeps showing `0.6.0` — that is
> expected, because the agent did not change.
