## ApiLens v0.6.1 — 빈 공간 회수 확대 + 절감 예측 기준 정정 | Reclaim more disk, predict savings correctly

**collector(server) 만 바뀌는 릴리스입니다. agent 를 다시 배포할 필요가 없습니다.** 정리
후 비어 있는 페이지를 정해진 몫만큼 반복해서 OS 에 돌려주도록 고쳤고, 계측 분석 화면의
절감 예측을 **디스크에 실제로 저장된 크기** 기준으로 바로잡았습니다. 어느 흐름에도 붙지
못한 기록을 야간 정리가 **이틀에 걸쳐 확인하고** 치우며, 비어 있던 마지막 정리 시각이
다시 채워집니다. 이전 문서에서 잘못 설명했던 두 가지도 함께 정정했습니다.
**DB 스키마 변경이 없으므로** collector jar 만 교체하고 재기동하면 됩니다.

**This release changes only the collector (server) — you do not need to redeploy the agent.**
Free pages are now returned to the OS in repeated, budgeted rounds after cleanup; the
instrumentation-analysis screen now predicts savings from the **bytes actually stored on
disk**; records that never got attached to a flow are swept by the nightly cleanup **after
being confirmed on two consecutive nights**; and the "last cleanup" timestamp is restored
when its row is missing. Two incorrect statements in earlier docs are corrected.
**No schema migration** — just replace the collector jar and restart.

---

### 새로운 기능 | What's new

- **정리 후 빈 공간 회수 확대** — 야간 정리가 끝난 뒤 비어 있는 페이지를 **정해진 몫만큼 반복해서** OS 에 돌려줍니다. 이전에는 회수 명령이 한 번 부를 때 한 페이지씩만 진행돼 사실상 회수가 보이지 않았습니다.
  - 그 결과 설정 페이지에서 [지난 데이터 정리] 를 눌렀을 때 나오는 **"약 X 확보" 숫자가 눈에 띄게 커집니다.** 오류가 아니라 원래 그랬어야 하는 값입니다.
  - 얼마나 회수되는지는 그동안 쌓인 양에 달려 있어 이 노트는 수치를 단정하지 않습니다. 실행 전후로 DB 파일 크기를 직접 비교하세요.
  - ⚠️ **돌려받은 공간은 영구적이지 않습니다.** 트래픽이 늘면 파일은 다시 그만큼 자랍니다. 파일 크기를 계속 낮게 유지하려면 보관 기간을 줄이거나 계측량 자체를 줄이는 편이 근본적입니다.
- **고아 기록 자동 정리 (이틀에 걸쳐 확인)** — 어느 흐름에도 붙지 못한 기록(요약 행이 없는 기록)을 야간 정리가 치웁니다.
  - **첫 밤에 후보로 적어 두고, 다음 밤에도 여전히 고아인 것만 지웁니다.** 요약이 늦게 도착한 기록을 죽이지 않기 위한 유예입니다. 그래서 "즉시 사라진다" 가 아니라 **"이틀에 걸쳐 확인하고 지운다"** 입니다.
  - **수동 [지난 데이터 정리] 는 이 정리를 하지 않습니다.** 버튼을 연달아 눌러도 고아 기록은 그대로입니다. 되돌릴 수 없는 수동 조작인 [전체 삭제] 만 유예 없이 그 자리에서 함께 지웁니다.
  - ⚠️ 이 정리는 **증상을 치우는 것이지 고아가 생기는 원인을 고치는 것이 아닙니다.** 원인 해소는 이후 버전 과제로 남습니다.

### 달라진 점 | Changed

- **계측 분석의 절감 예측 기준을 "실제 저장 크기" 로 교체** — 클래스별 payload 용량과 "빼면 이렇게 돼요" 절감량을, 자르기 전 원본 크기가 아니라 **디스크에 실제로 저장된 본문 길이**로 계산합니다.
  - **무엇이 달라 보이나**: 화면 라벨과 표 구성은 그대로이고, payload 용량 숫자와 절감량 숫자만 내려갑니다.
  - **왜 결론이 달라질 수 있나**: 본문이 잘려 저장된 기록이 많은 클래스일수록 이전 값이 실제보다 컸습니다. 그래서 **클래스 간 순위가 바뀔 수 있습니다** — 이전에 이 화면을 보고 제외 대상을 정했다면 한 번 다시 확인하시길 권합니다.
  - **적용 범위**: 계산 기준만 바뀌었습니다. 저장된 데이터·수집 방식·화면 라벨은 그대로입니다.
- **마지막 정리 시각이 다시 채워집니다** — 정리 시각을 담는 행이 사라져 있으면 이전에는 갱신이 조용히 실패해 설정 페이지에 "정리 이력 없음" 이 계속 남았습니다. 이제 그 행을 **다시 만들면서 기록**하고, 조회 시점에 행이 없으면 서버 로그에 경고를 남깁니다.
  - ⚠️ 행이 왜 사라졌는지는 **아직 규명하지 못했습니다.** 이 변경은 **"고쳤다" 가 아니라 "다시 생기면 로그로 알 수 있게 했다"** 입니다.
- **진입점 없는 흐름 차단 옵션의 영향 범위 정정** — 이전 문서는 이 옵션을 켜면 **"배치 워커 흐름"** 이 사라진다고만 적었습니다. 실제로는 **진입점 밖에서 시작되는 흐름 전반**이 사라집니다 — 배치 워커는 대표적인 예일 뿐이고, 메시지 소비자·이벤트 리스너, 애플리케이션 기동·종료 작업, **요청에서 갈라져 나온 별도 스레드**(비동기 실행·별도 스레드 풀에 넘긴 작업)에서 시작되는 흐름도 함께 사라집니다. 옵션의 동작이 바뀐 것이 아니라 **설명이 좁았던 것**입니다. 기본값은 여전히 꺼짐이고, 켜지 않으면 동작은 이전과 완전히 같습니다.

### 이전 버전 설명 정정 | Corrections to earlier docs

- **`incremental_vacuum` 의 한도** — 이전 문서·주석은 "파일 끝(tail)의 free page 만 회수한다" 고 적었습니다. **그것은 잘못된 설명이었습니다.** 이 명령은 비어 있는 페이지를 전량 회수할 수 있고, 회수가 거의 안 보였던 진짜 이유는 **한 번 부를 때 한 페이지씩만 진행되기 때문**이었습니다. 남는 한도는 **"한 번에 정해진 몫만 회수한다"** 입니다. 정리 후 `freedBytes` 가 삭제량보다 작게 나올 수 있다는 서술 자체는 **여전히 맞고**, 사유만 바뀌었습니다.
- **진입점 없는 흐름 차단 옵션의 영향 범위** — 위 「달라진 점」의 마지막 항목을 참고하세요.
- 이미 발행된 v0.6.0 노트는 고치지 않습니다. 정정 내용은 이 노트와 `CHANGELOG.md` 에 남깁니다.

### 밀린 빈 공간을 한 번에 돌려받기 (권장 1회 작업) | One-time reclaim

야간 정리는 한 번에 정해진 몫만 회수하므로, 오랫동안 쌓인 빈 공간은 아래 절차로 한 번 정리한 뒤
야간 정리에 맡기는 편이 빠릅니다. **1회성 작업**이며 평소에는 필요 없습니다. 자세한 설명은
`docs/api.md` 의 「밀린 빈 공간을 한 번에 돌려받기」 절에 있습니다.

1. 그날 회수 가능한 양을 먼저 확인합니다 — `sqlite3 apilens.db "PRAGMA freelist_count;"`. 0 이면 할 일이 없습니다.
2. **수집기(collector)를 먼저 멈춥니다.** SQLite 는 쓰기를 한 번에 하나만 허용해 적재와 회수가 서로 기다리고, 작업 중 들어오는 쓰기가 `-wal` 파일을 계속 키웁니다.
3. ⚠️ **명령 실행 직전에 DB 파일을 백업합니다** — `cp apilens.db apilens.db.bak` (`-wal` / `-shm` 파일도 함께 두세요).
4. ⚠️ **여유 디스크를 확인하세요 — 위 3번 백업과 아래 5번 회수가 둘 다 디스크를 씁니다.** 백업 사본이 현재 DB 크기만큼 쓰고, 회수가 도는 동안 `-wal` 파일이 빈 페이지 **1,000개당 대략 10~20 MB** 까지 자랍니다(빈 페이지가 20만 개면 2~4 GB 규모). 여유가 모자라면 회수가 도중에 실패하고 호스트 디스크가 가득 차 **다른 프로그램까지 영향을 받을 수 있습니다.** 자세한 어림값과 그 한계는 `docs/api.md` 의 같은 절에 있습니다. **야간 정리의 자동 회수에는 이 확인이 필요 없습니다** — 그쪽은 몫이 정해져 있고 실행 전에 디스크 여유를 스스로 확인합니다.
5. 회수 — `sqlite3 apilens.db "PRAGMA incremental_vacuum(-1); PRAGMA wal_checkpoint(TRUNCATE);"`
6. 1번에서 본 빈 페이지가 파일 크기에서 빠집니다. 줄어드는 양은 그동안 쌓인 양에 달려 있으므로 실행 전후 파일 크기를 직접 비교하세요.
7. **[최적화] 버튼과는 다른 작업입니다** — 그쪽은 중간 단편화까지 재배치하는 전체 VACUUM 입니다. `docs/api.md` 의 정리 절을 참고하세요.
8. **돌려받은 공간은 영구적이지 않습니다.**

### 업그레이드 | Upgrade

- **collector(server) jar 만 교체하고 재기동하면 됩니다.** **agent 를 다시 배포할 필요가 없고**, 대상 앱 JVM 재시작도 필요 없습니다.
- **DB 스키마 변경이 없습니다** — 마이그레이션이 실행되지 않으므로 되돌릴 수 없는 변경도 없습니다. (그래도 위 1회 회수 작업을 한다면 그 직전에 백업하세요.)
- **API 호환** — 경로·요청·응답의 필드 구성이 그대로입니다(추가·삭제·타입 변경 0). 다만 계측 분석의 payload 용량이 내려가고, 정리 후 "확보한 공간" 숫자가 커지며, 마지막 정리 시각이 채워지는 등 **값이 달라집니다.**
- **agent 버전 라벨은 `0.6.0` 으로 계속 보입니다.** 이번에 agent 를 바꾸지 않았다는 뜻이며 정상입니다.

> **Collector-only release — no agent redeploy needed.** Replace the collector jar and
> restart. **No schema migration**, so nothing irreversible happens on startup. API contracts
> are unchanged field-for-field, but some **values** change: payload sizes on the analysis
> screen now reflect bytes actually stored (savings estimates go down and class ranking may
> shift — re-check before excluding), the "freed space" number after cleanup grows, and the
> last-cleanup timestamp is restored when its row is missing. Orphan records are swept by the
> nightly cleanup only after being confirmed on two consecutive nights; the manual cleanup
> button does not sweep them. If disk has been piling up, run the one-time reclaim above
> (stop the collector and **back up the DB file first**). The agent version label keeps
> showing `0.6.0` — that is expected, because the agent did not change.
