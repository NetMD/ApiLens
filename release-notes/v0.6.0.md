## ApiLens v0.6.0 — 재시작 없는 원격 계측 설정 + 계측량 제어 손잡이 | Remote instrumentation control without restarts

**agent + collector(server) + 화면이 모두 바뀌는 릴리스입니다.** 핵심은 계측량을
운영 중에 줄이는 손잡이입니다 — 서비스별 계측 설정을 화면에서 저장하면 **JVM 재시작
없이** agent 에 전달되어 적용됩니다(안전을 위해 **줄이는 방향만**). weaving 옵션으로는
뺄 수 없던 MyBatis mapper 도 **화면에 보이는 이름 그대로** 제외할 수 있습니다.
진입점이 아닌 곳에서 시작되는 조각 흐름을 원천에서 만들지 않는 옵션(기본 꺼짐),
좋은 조합을 영구화하는 `-D` 옵션 생성기, 에러 기록의 stack trace 본문, 적재 경합
카운터 표시가 함께 들어갑니다. **agent 가 바뀌는 릴리스라 agent jar 재배포 + 대상 앱
JVM 재시작이 필요**하고, **DB 에 테이블 하나가 추가**되므로 올리기 전 DB 파일 백업을
권합니다.

**This release changes the agent, the collector (server), and the UI.** The headline is a
lever to reduce instrumentation volume **while your app is running** — save a per-service
instrumentation config on the new screen and it reaches the agent **without a JVM restart**
(reduce-only, by design). MyBatis mappers, which the weaving exclude option cannot remove,
can now be excluded **by the exact name you see on screen**. Also included: an option that
stops flows starting outside an entry point (off by default), a `-D` option generator to make
a good combination permanent, stack trace bodies on error records, and ingest-contention
counters. **Because the agent changes, redeploy the agent jar and restart the host JVM.**
**One table is added to the database** — back up your DB file before upgrading.

### 새로운 기능 | What's new

- **원격 계측 설정 (재시작 없이, 줄이는 방향만)** — Services 목록의 `계측 설정` 버튼으로 서비스별 설정을 편집·조회·철회합니다. 항목은 4가지: JDBC 파라미터 캡처 끄기 · JDBC 결과 캡처 끄기 · 진입점 없는 흐름 차단 켜기 · 개별 제외 목록. 각 항목은 3상태(지시 없음 / 줄이기 / 기동값으로 되돌리기)로 고르며, "지시 없음" 항목은 저장에 실리지 않아 한 항목만 바꿔도 나머지가 의도치 않게 확정되지 않습니다. 화면 없이 API(curl)로도 같은 일을 할 수 있습니다.
  - **판정은 agent 안에서** — agent 는 JVM 시작 `-D` 값을 기준점으로 **줄이는 방향(및 시작값 복귀)만** 적용하고, 기준점을 넘는 확대 지시는 버립니다. server 를 신뢰하지 않는 구조라, server 가 오염되어도 계측이 몰래 넓어지지 않습니다.
  - **MyBatis mapper 개별 제외** — weaving 제외 옵션으로 못 빼던 mapper 를 화면 이름 그대로 뺄 수 있습니다.
  - ⚠️ **개별 제외 목록을 원격으로 전부 비우는 지시는 전달되지 않습니다** — 빈 목록 저장은 "지시 없음"이 되어(철회와 같음) agent 에 이미 적용된 목록은 그대로 남습니다. 걸린 제외를 풀려면 남길 항목만으로 저장하거나 JVM 을 재시작하세요. 같은 안내가 화면에도 항상 표시됩니다.
- **진입점 없는 흐름 차단 옵션 (`apilens.instrument.require-entry-root`, 기본 꺼짐)** — 켜면 진입점(들어오는 요청을 받는 controller 계층)이 아닌 곳에서 시작되려는 흐름을 만들지 않습니다. 조상을 계측에서 빼면 말단이 새 시작점이 되어 조각 흐름이 쏟아지는 문제를 원천에서 막는 레버입니다. **켜면 배치 워커(@Scheduled/@Async 류) 흐름이 통째로 남지 않으며, 그것이 이 옵션의 목적입니다 — 그래서 기본값이 꺼짐입니다.** 켜지 않으면 동작이 이전과 완전히 같습니다.
- **`-D` 옵션 문자열 생성기** — 원격 설정 화면과 같은 자리에서, 화면으로 시험해 확정한 조합을 JVM `-D` 옵션 한 줄로 만들어 복사합니다. 원격 값은 메모리에만 있으므로, 재시작 후에도 유지하려면 이렇게 `-D` 로 영구화하세요. 기본값과 다른 것만 출력하고, MyBatis 전량 제외 선택지와 그 트레이드오프 안내를 함께 보여 줍니다.
- **에러 기록에 stack trace 본문** — 에러 기록의 속성에 원인 사슬(`Caused by:`)을 포함한 stack trace 가 담깁니다(4,096자 넘으면 뒤쪽을 잘라 표시). 화면의 에러 박스에서 유형·메시지에 더해 발생 지점 스택을 볼 수 있습니다.
- **적재 경합 카운터 표시** — 설정 페이지 "데이터 관리" 섹션과 유지보수 상태 조회 응답에서 적재 경합(`SQLITE_BUSY`) 발생 횟수와 유실 청크 수를 볼 수 있습니다. **0 이 정상값**이며, 카운터는 메모리에만 있어 server 재시작 시 0 으로 돌아가는 것도 정상입니다(누적 기준선은 `logs/apilens.log` 로 비교).

### 달라진 점 | Changed

- **첫 화면 로딩 개선** — UI 를 화면 단위 파일로 나눠 첫 로딩에 내려오는 양을 줄였습니다. 무거운 차트·그래프 라이브러리는 해당 화면을 열 때 내려옵니다.
- **agent 버전 라벨의 의미 명시** — Services 화면의 agent 버전이 **"마지막 확인 시점의 버전"** 임을 라벨과 설명으로 밝힙니다. collector 가 꺼져 있는 동안 agent 가 시작하면 이전 값이 남아 있을 수 있어, 지금 버전이라고 단정하지 않습니다.
- **서비스 삭제 시 원격 계측 설정 동반 삭제** — 서비스를 지우면 그 서비스의 저장된 지시도 함께 철회됩니다(trace 데이터는 여전히 보존). 철회 의미 그대로 — agent 에 이미 적용된 값은 되돌아가지 않습니다.
- **server 로그 위생** — 기본 로그 레벨을 INFO 로 조정하고, 커넥션 풀이 시계 역행(시스템 시각이 뒤로 이동)을 감지할 때 반복해서 내던 경고를 메시지 조건으로만 걸러냅니다. 같은 로거의 다른 신호(스레드 기아 경고 등)는 그대로 남습니다 — 로그 잡음을 줄이는 것이지, 시계 역행 감지 자체를 없애는 것이 아닙니다.
- **보관 정리의 배치 사이 양보** — 정리(cleanup/purge)가 배치 트랜잭션 사이에 짧게 멈춰, 정리가 도는 동안에도 적재·조회가 끼어들 틈을 보장합니다(삭제 순서·정확성은 그대로).

### 업그레이드 | Upgrade

- **순서: collector(server) 먼저 → agent 나중.** 구 agent 는 새 응답 필드를 읽지 않으므로 이 순서면 그 사이에도 수집이 끊기지 않습니다.
- ⚠️ **DB 파일 백업을 먼저 하세요.** 새 collector 를 기동하면 테이블 하나를 추가하는 변경이 자동으로 적용되고, **이 변경은 되돌릴 수 없습니다.** 0.6.0 으로 한 번 올린 DB 파일을 이전 collector 로 다시 열지 마세요. 되돌려야 한다면 백업한 파일로 복원하고 이전 jar 로 기동하세요. 기존 테이블·데이터에는 영향이 없습니다.
- **agent jar 재배포 + 대상 앱 JVM 재시작이 필요합니다.** 이번 릴리스의 새 동작(원격 설정 적용·진입점 없는 흐름 차단·stack trace 본문)은 새 agent 에서만 유효합니다. 재배포하지 않아도 구 agent 는 기존대로 동작하지만(무파손), 화면의 agent 버전은 이전 값으로 보일 수 있습니다.
- **API 호환** — 적재 응답은 기존 필드가 그대로이고, 원격 설정을 저장한 서비스에만 필드 하나가 추가로 실립니다(없으면 필드 자체 생략). 기존 조회 API 응답도 그대로입니다.

> **Upgrade order: collector (server) first, agent second.** Old agents ignore the new
> response field, so ingestion keeps working in between. ⚠️ **Back up your DB file first**:
> starting the new collector automatically adds one table, and **that change cannot be
> undone** — do not reopen an upgraded database with an older collector; restore from backup
> instead. **Redeploy the agent jar and restart the host JVM** to get the new behaviors
> (remote config, entry-root gating, stack trace bodies). Without redeploying, old agents
> keep working as before, but the version column may show a stale value. Existing API
> contracts are unchanged; the ingest response gains one optional field only for services
> with a saved config.

### 주의 | Notes

- **원격 설정은 영구 설정이 아닙니다.** 원격 값은 agent 메모리에만 있어 JVM 을 재시작하면 시작 `-D` 값으로 돌아갑니다. 유지하려면 `-D` 생성기로 영구화하세요.
- **화면은 JVM 시작 `-D` 값을 알지 못합니다.** 그래서 지시가 그대로 적용된다고 단정하지 않습니다 — 줄이는 지시와 시작값 복귀 지시만 적용되고, 시작값을 넘는 확대 지시는 agent 가 버립니다.
- **저장된 지시가 없는 서비스의 설정 화면이 비어 있는 것은 정상입니다.** 오류가 아니라 "아직 지시 없음" 상태이며, 그 자리에서 바로 첫 저장을 하면 됩니다.
- **경합 카운터가 0 인 것도, 재시작 후 0 으로 돌아가는 것도 정상입니다.** 값이 늘어난다면 한 번에 큰 흐름이 들어오는 시간대를 의심하고, 계측 분석 화면과 계측 설정으로 계측량을 줄이는 것을 검토하세요.
- **agent 버전은 마지막 확인 시점의 값입니다.** collector 가 꺼져 있는 동안 agent 가 시작했다면 이전 값이 남아 있을 수 있습니다 — 배포 실패가 아닐 수 있으니, agent 를 다시 시작하면 그때 도착하는 값으로 갱신됩니다.

> Remote config is **not persistent** — it lives in agent memory and reverts to the startup
> `-D` values on restart; use the generator to make it permanent. The screen does not know
> your startup `-D` values, so it never claims a directive will apply as-is: reduce and
> back-to-startup directives apply, widening directives are dropped by the agent. An empty
> config screen means "no directive yet", not an error. Contention counters at 0 (and
> resetting to 0 after a restart) are normal. The agent version column shows the last
> confirmed value — a stale value does not necessarily mean a failed deployment.
